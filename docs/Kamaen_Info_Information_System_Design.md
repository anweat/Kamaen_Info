# Kamaen Info 信息系统与模型模拟设计定稿

版本：v0.4 Concept Draft  
状态：概念收束稿。本稿重点明确模型运行、参数/算子、内外网、触发任务、硬件性能、全光五件套映射之间的关系；后续开发时再拆分为具体 Block、Item、Data Component、BlockEntity、网络包与外部服务接口设计。  

## 1. 定位

本方向不是把神经网络包装成普通科技产线，也不是在 Minecraft 服务端 tick 内直接运行真实大模型，而是把计算机科学、信息学、控制、通信、数据分析与机器学习抽象为一套可搭建、可观察、可调参、可部署的模型运行系统。

类比机械与航空类模组对物理、动力、气体、飞控的模拟，本系统希望让玩家在游戏中研究：

- 世界信息如何被传感器量化为结构化数据。
- 参数、算子、状态、路由和反馈如何组成模型。
- 同一模型内部不同子块如何异步触发和协同推理。
- 模型如何通过内网组织计算，通过外网采集数据、调用服务和下发动作。
- CPU、GPU、NPU、内存、存储、带宽如何分别影响推理、训练、路由、脚本和传感器。
- 模型或控制器如何反过来影响生物、物流、机器、对话、交易、对抗和合作行为。

核心体验应当是“搭建一个信息系统并研究它为什么有效”，而不是单纯合成最终级物品。

## 2. 模型运行闭环

基础闭环：

```text
世界状态
-> 传感器采样
-> 类型化数据
-> 脚本器预处理/融合
-> 模型外网输入
-> 模型内网调度
-> 参数空间/算子网络推理
-> 输出路由
-> 执行器影响世界
-> 反馈信号回流
-> 参数、状态、结构或策略更新
```

这个闭环可以完全使用游戏内简化数值规则，也可以通过外部 API 或本地训练后端接入真实框架。游戏内负责定义数据、模型结构、路由、约束、指标、可视化和调度；外部后端只作为可选的训练、推理或优化扩展。

## 3. 核心数据分类

模型运行时应明确区分四类数据：

- Input：本次推理或训练传入的数据，例如传感器向量、物品标签、局部地形网格。
- Parameter：长期保存、可训练或可调的值，例如权重、偏置、PID 参数、路径代价、门控权重。
- State：跨 tick 保存的运行记忆，例如 RNN hidden、积分项、历史摘要、优化器动量。
- Activation：单次运行中的中间结果，例如层输出、融合向量、注意力权重、局部评分。

这四类数据生命周期不同：

- Parameter 保存在模型物品、参数空间或参数库中。
- State 随模型运行持续存在，但可以 reset、冻结或摘要化。
- Activation 应由运行时临时分配，结束后释放或复用缓存。
- Input 来自外部传感器、脚本、通信网络或上游模块。

后续光学算力优化、状态缓存估算、量化、缓存复用和外部训练导出都依赖这个区分。

**光计算阶段（第 6 阶段后）四分类在全光系统上的映射**：

| 数据类 | 全光系统中位置 |
|--------|--------------|
| Input | 光协处理器编码注入各单元的输入光场 |
| Parameter | 光GPU MZI 相位偏置（稳态）；光脉冲处理器腔体调谐参数（稳态）|
| State | 光RAM 循环腔内光子强度；光控制核双稳态晶胞当前态 |
| Activation | 光GPU / 光脉冲处理器的输出光场；在光域内直接传递至下一单元 |

InfoSignal 的 `frequency_vector` 字段在第 6 阶段后扩展为承载光路信息：

```text
frequency_vector: {
  primary_freq: F1 | F2 | F3 | F4 | F5,
  optical_wavelengths: [λ1, λ2, ...],  # 第 6 阶段后新增；非光路 InfoSignal 留空
  coherence_state: 0.0 – 1.0,          # 第 6 阶段后新增
  excitation_phase: 0.0 – 2π,          # 第 6 阶段后新增；激发相位（费曼描述模式用）
}
```

旧 InfoSignal（仅 primary_freq）继续兼容，新字段为可选。详见 `docs/Kamaen_Info_Optical_Computing_Design.md`。

loss、reward、metric、feedback 不应被设计为第五种特殊数据。它们是普通数据节点在训练、评价或调度语境下的语义角色：可以由传感器直接采集，也可以由算子从 Input、State、Activation 或世界观测中计算得到，再经路由送往优化器、状态更新器、日志或外部训练节点。

## 4. 参数存放单元

参数不是方块本身，方块只是参数的可视化、寻址、编辑和封装入口。运行时应把参数打包为连续缓冲区。

### 4.1 游戏表现

建议提供几级参数存放单元：

- 参数晶胞：最小可视化参数单位，适合少量标量或教学展示。
- 参数矩阵板：存储一块向量、矩阵、卷积核或嵌入表。
- 参数晶体簇：组合多个参数矩阵，适合一层或一个子模块。
- 参数库：高级存储结构，负责打包、索引、版本、冻结、复制、量化和外部导出。

### 4.2 参数元信息

每个参数至少需要记录：

```text
id
shape
dtype
value 或 buffer_ref
gradient
optimizer_state
quantization
version
scope
owner
trainable/frozen/shared
```

示例：

```text
id = param.layer1.weight
shape = [16, 32]
dtype = int8
scale = 0.03125
zero_point = 0
buffer_ref = bank_03:offset_2048
trainable = true
```

### 4.3 运行时原则

多个参数方块在保存或启动模型时被打包为：

```text
ParameterBuffer
QuantizedBuffer
OptimizerStateBuffer
```

模型中所有有参数算子都引用这些缓冲区，而不是在运行时逐个扫描方块。这样才能支持矩阵加速、批量更新、参数复制、模型版本管理、外部训练导出和光学算力成本估算。

## 5. 算子与封装模块

算子是接收输入、引用参数和状态、执行运算并返回输出的计算单元。统一形式：

```text
outputs = op(inputs, parameters, states, config)
new_states = state_update(...)
```

### 5.1 算子类型

- 无参数算子：固定运算，例如 ReLU、Normalize、Concat、Pool、Compare、Route。
- 有参数算子：引用可训练或可调参数，例如 Linear、Conv、Embedding、Gate、PID、RNNCell。
- 有状态算子：保存跨 tick 状态，例如 MovingAverage、Memory、RNN、PID 积分项、经验回放。
- 黑盒算子：外部 API、自定义脚本或无法优化的复杂逻辑。

### 5.2 有参数算子的统一封装

有参数算子不需要表现为“带权重的特殊方块”。它可以被封装为一个模块：

```text
输入路由 -> 参数方块/状态方块 -> 内部脚本或子算子网络 -> 输出路由
```

例如线性层模块：

```text
input: x
parameters: W, b
script: y = matmul(x, W) + b
output: y
```

例如 PID 模块：

```text
input: error
parameters: kp, ki, kd
states: integral, last_error
script: control = kp*error + ki*integral + kd*(error-last_error)
output: control
```

这意味着 Linear、Conv、PID、RNNCell、MoE Gate、路径代价估计器等都可以使用同一套参数方块、路由 ID、状态寄存器和封装规则。

### 5.3 原生算子、脚本算子与编译

建议分三层：

- 原生算子：系统内置，高性能，可被硬件层估算成本，例如 matmul、conv2d、add、mul、activation、pool、concat、normalize。
- 脚本算子：玩家用脚本组合原生算子，例如 `relu(matmul(x, W) + b)`。
- 黑盒算子：无法静态优化的自定义脚本或外部调用。

脚本方块主要用于描述运算和批量处理，不应长期以文本解释方式高频运行。保存或启动模型时，系统应尽量将脚本编译为标准算子图：

```text
脚本/方块结构
-> ID 解析
-> 类型检查
-> shape 推导
-> 拓扑排序
-> 参数打包
-> 算子融合
-> 成本估算
-> ExecutableGraph
```

可识别模式应优化为高性能原生算子，无法识别的部分才回退到通用脚本执行。

## 6. 参数空间与模型物品

参数空间是模型内部结构的实体化表达。玩家进入自定义维度后摆放参数、算子、状态、触发器、内网路由、反馈路径和脚本器，退出后保存为单一模型物品。

模型物品应保存：

- 结构图。
- 参数缓冲区。
- 状态定义。
- ID 映射。
- 内网路由表。
- 外网导出入口。
- 量化配置。
- 版本信息。
- 性能估算与编译缓存。

支持能力：

- 复制。
- 嵌套。
- 冻结权重。
- 继续训练。
- 只复制结构。
- 只复制参数。
- 参数共享。
- 外部导出与回写。

参数空间本质上是一台微型计算机，内部拥有局部地址空间、内部触发器、激活缓存、状态寄存器、参数库、子图调度器和模型网关。

## 7. 模型内网与模型外网

为了区分模型内部计算和系统级通信，网络分为模型内网与模型外网。

### 7.1 模型内网

作用范围：一个参数空间、一个模型物品或一个封装模块内部。

负责：

- 局部 ID 寻址。
- 模型块之间的异步触发。
- 激活值传递。
- 内部反馈回流。
- 状态提交。
- 子模块调用。
- 内部广播/组播。
- 局部缓存复用。
- 嵌套模块命名空间。

例子：

```text
reflex 子图：每 tick 运行，负责低延迟反应。
memory 子图：每 5 tick 更新历史摘要。
planner 子图：每 20 tick 规划路径。
optimizer 子图：后台接收反馈并更新参数。
```

模型内网成本主要来自：

- local_id 查询。
- 子图调度。
- 激活路由。
- 状态提交。
- 本地广播。
- shape 检查。
- buffer 分配和复用。

静态内网 ID 应在编译时转为整数 handle，避免运行期字符串查找。

### 7.2 模型外网

作用范围：模型与世界、传感器、执行器、远程节点、存储节点、中心训练机、无线网络和外部 API 之间。

负责：

- 远距离传感器采集。
- 多传感器协调。
- 模型服务调用。
- 数据上传。
- 参数同步。
- 模型下发。
- 外部 API 请求。
- 跨机器、跨区块、跨维度通信。
- 权限、认证、重传、超时、限流。

模型外网成本主要来自：

- packet 序列化。
- 路由跳数。
- 带宽占用。
- 传输延迟。
- 权限检查。
- 重试与超时。
- 跨维度传输。
- 外部服务等待。

### 7.3 ID 作用域

建议定义三类 ID：

```text
local:memory.hidden
export:action.move
remote:base.training_server.dataset_queue
```

- local：模型内网 ID，最快，适合子图、参数、状态和激活。
- export：模型暴露给外部访问的入口或出口。
- remote：外网地址，跨机器、跨区块、跨维度或外部服务访问。

嵌套模块自动生成命名空间，防止复制和复用时冲突。

### 7.4 端口声明与连接规则

模型内网、模型外网和硬件网络都应使用统一端口声明，避免玩家靠猜测判断某个面能不能接线。

端口基础字段：

```text
port_id
side
direction: input/output/bidirectional
scope: internal/external/hardware/sensor
protocol: model_data/frequency_bus/fiber/wireless/storage/control/redstone
frequency_tier
bandwidth
packet_types
permission_scope
```

端口决定三件事：

- 能接什么线或背板。
- 能传什么数据包。
- 会消耗哪一类硬件预算。

典型端口：

```text
InputPort：Input、SensorFrame、RemoteRequest。
ActivationPort：Activation、TensorChunk、StateRef。
ParameterPort：ParameterRef、ParameterPage、ParameterDelta。
ControlPort：Trigger、ControlCommand、RedstoneMapping。
StoragePort：DatasetShard、ModelSnapshot、StoragePage。
FeedbackPort：Metric、Reward、Loss、Gradient。
```

高级网关、交换机或模型封装器可以重映射端口方向，但重映射应消耗路由预算、频率通道或结构槽位。

### 7.5 模型组件方块网络

模型组件方块是参数空间和模型物品之外的实体化编辑方式。玩家可以用方块搭出一个局部计算图，然后由模型编译器扫描并保存为可执行模型。

基础组件：

```text
input_gateway：把外部传感器、物品、红石、网络包转换为 Input。
operator_block：声明原生算子或脚本算子。
parameter_block：引用参数页、参数矩阵板或参数库。
state_register：保存跨 tick 状态。
activation_bus：传递临时激活。
trigger_block：提交内部或外部任务。
output_gateway：输出到执行器、网络、数据物品或红石。
feedback_node：把 loss、reward、metric 回流到模型。
model_compiler：扫描组件网络，生成 ExecutableGraph。
```

设计自由度：

- 拓扑自由：串联、并联、残差、反馈、分支、门控和子模块调用。
- 命名自由：local/export/remote 地址由网关和命名空间决定。
- 部署自由：小模型单机运行，大模型拆到多个硬件节点。
- 优化自由：合批、缓存、量化、静态 shape 和局部编译都能改变成本。
- 接口自由：同一模型可接传感器网、工厂控制网、光纤集群和无线外网。

实现边界：

- 结构变化、保存或手动编译时扫描组件网络。
- 运行时使用编译后的静态图和端口表。
- 不每 tick 遍历全部模型方块。
- 高频文本脚本必须先编译为数据处理图或受预算限制。
- 组件网络可以导出为模型物品，便于复制、版本管理和部署。

## 8. 触发器与任务调度

触发器不只是红石式激活器，而是任务提交与子图调度系统。它既负责外部任务，也负责同一模型内部不同步模块的运行。

### 8.1 内部触发器

内部触发器属于模型内网，负责：

- run_subgraph：运行某个子图。
- route_activation：转发激活值。
- update_state：更新状态。
- apply_local_feedback：应用局部反馈。
- call_child_module：调用嵌套模块。
- commit_tick：提交本 tick 状态。

触发模式：

- 每 tick。
- 固定周期。
- 输入到齐。
- 条件满足。
- 反馈到达。
- 子模块完成。
- 状态变化。

### 8.2 外部触发器

外部触发器属于模型外网或系统级调度，负责：

- sample_sensor：请求传感器采样。
- send_packet：发送网络包。
- call_service：调用模型服务。
- upload_dataset：上传训练数据。
- download_model：下载模型或参数。
- invoke_api：调用外部 API。
- register_service：注册长期任务。

触发模式：

- 一次性触发。
- 周期触发。
- 条件触发。
- 事件触发。
- 阈值触发。
- 外部消息触发。
- 后台常驻服务。

### 8.3 CPU 关联

触发器提交任务，调度器决定任务何时运行、在哪里运行、是否合批、是否降级、是否超时、是否回调。无论是内部触发还是外部触发，都消耗 CPU 预算。

任务元信息建议包含：

```text
task_type
scope: internal/external
target_id
input_refs
priority
deadline
repeat_mode
callback_route
estimated_cost
```

## 9. 路由系统

“路由方块”不是单一方块，而是通信系统各类元件的统称。它包括模型内网 ID 族、局域通信、远距离采集、多传感器协调、服务发现、消息队列和跨维度网关。

路由系统包括：

- 模型内路由：参数空间内部的 ID 寻址、输入输出绑定、反馈回流。
- 局域路由：同一机器组或基地内的数据总线。
- 远程路由：无线、定向天线、中继、跨区块、跨维度。
- 传感器协调：多传感器同步采样、时间戳对齐、数据融合。
- 服务发现：类似 DNS，把名称解析到模型、传感器、执行器或存储节点。
- 会话连接：类似 socket，建立持续输入输出通道。
- 消息队列：异步上传训练数据、日志、反馈和模型版本。
- 广播/组播：多实体协作、群体控制、对抗训练环境同步。

路由会消耗 CPU 与带宽，因为它涉及：

- ID 解析。
- 路由表查询。
- 权限检查。
- 包封装/解包。
- 序列化/反序列化。
- 压缩/解压。
- 时间戳对齐。
- 缓存读写。
- 重传/确认。
- 广播复制。
- 队列调度。

因此模型优化不仅是减少参数量，也包括减少动态查询、远程传输、广播、重复采样和无意义路由跳数。

## 10. 模型与算力各部分的关联

本系统不做电气电脑模拟器。模型与算力分三层：第 5 阶段以前是 `InfoSignal`、频率总线和信号缓存组成的信息模型；第 6 阶段以后是玩家摆出的结构模型；真正的高阶算力由全光五件套承担。

### 10.1 光控制核负责的部分

第 5 阶段没有电气 CPU。控制与调度由频率总线、信号缓存、红石边界触发和手动/自动调谐阵列完成；第 6 阶段起，**光控制核（`photonic_control_core`）**以全光有限状态机承担模型内部控制与调度。

光控制核主要负责控制、调度和 I/O：

- 内部触发器调度（光逻辑门驱动的 FSM 状态转移）
- 外部触发器任务提交（光路由交换机输出派发信号）
- 路由表查询（光控制核状态寄存器 + 光逻辑门实现）
- ID 解析
- 脚本预处理（编译后的光逻辑图）
- 传感器协调
- 协议处理
- 序列化与反序列化
- 权限与认证
- 状态机（双稳态晶胞阵列）
- 小模型或低频推理
- 任务队列和回调

光控制核成本可以细分为：

```text
control_ops：触发器、FSM 状态转移、任务调度（双稳态晶胞 + 光逻辑门）
route_ops：地址解析、路由转发、包处理（光路由交换机）
script_ops：脚本预处理、数据转换（编译后光逻辑图）
sensor_ops：采样协调、数据整理
io_ops：存储、网络、序列化（与光RAM 协同）
```

玩家没有运行大矩阵时也可能遇到瓶颈，因为传感器、路由、脚本和同步会吃满信息链路或光控制核的逻辑预算。晶体品级不足时还会增加随机错误率，进一步消耗预算用于错误重试。

### 10.2 全光系统五件套分工（第 6 阶段）

中游计算不经过电气 GPU/NPU 占位。第 5 阶段只做信息组织：传感器读取、信号缓存、路由、红石边界触发和工艺调谐。第 6 阶段后由**光控制核 + 光GPU + 光脉冲处理器 + 光协处理器 + 光RAM** 五件套承担模型计算，详见 `docs/Kamaen_Info_Optical_Computing_Design.md`。

第 6 阶段所有模型内部信号传递路径均为光子，媒介是光的激发与湮灭。红石和 FE 只保留在边界触发、供能和安全停机中。

**第 6 阶段后的五件套分工**：

- **光控制核（`photonic_control_core`）**：全光有限状态机。卡玛恩晶体双稳态腔 + 光逻辑门阵列实现分支与控制流。
  - 承担：`control_ops`、`route_ops`、`script_ops`、`sensor_ops`、`io_ops`
  - 晶体品级直接影响逻辑门保真度；低品级导致随机位翻转

- **光GPU（`photonic_gpu_unit`）**：密集线性代数加速。基于 MZI 干涉网络做矩阵-向量乘法。
  - 适合：matmul、conv、FFT、大批量推理、固定权重、模型主干
  - 不适合：稀疏权重、快速权重切换、动态算子
  - 算子：`matmul_ops`、`conv_ops`、`fft_ops`

- **光脉冲处理器（`photonic_pulse_processor`）**：卡玛恩饱和吸收体 + 非线性腔处理稀疏激活和非线性算子。
  - 适合：稀疏激活、激活函数近似（ReLU/GELU/Sigmoid）、低精度时分处理
  - 算子：`sparse_ops`、`nonlinear_ops`、`pulse_ops`、`quant_ops`

- **光协处理器（`photonic_coprocessor`）**：光控制核调度下的纯光互连模块。高带宽数据通路。
  - 适合：批量光数据搬运、缓存间互连、零拷贝光总线、预处理
  - 算子：`data_move_ops`、`prep_ops`

- **光RAM（`photonic_ram_unit`）**：受激辐射循环腔短时存储。存放激活缓存和跨 tick 状态。
  - 承担：`state_hold_ops`
  - 寿命有限（20–80 tick），需光控制核定期刷新

**为什么全光可行**：卡玛恩晶体的 χ⁽²⁾ 非线性光学特性（由第 2–3 阶段向量爆破写入的应力张量决定）是游戏设定中光分支与光存储成立的物质基础。没有高品级专化晶体，全光系统无法稳定运行，这是早期晶体质量工作的直接回报。

**模型→硬件映射**：编译器扫描模型图后，把分支/调度派给光控制核，密集矩阵层派给光GPU，稀疏/激活层派给光脉冲处理器，数据搬运由光协处理器承担，短时状态由光RAM 持有。模型性能 = 算子图与全光五件套的匹配程度。

全光系统同样不适合频繁动态字符串路由、大量小任务和每 tick 解释脚本。玩家需要通过编译、合批、静态 shape 和参数打包让模型硬件友好，相干能预算也是新的优化维度。

### 10.3 物理结构即模型（第 6 阶段玩法）

第 6 阶段以后，模型不再只是 GUI 里的抽象网络。玩家摆放的光学方块拓扑就是模型架构，晶体与调谐器上的参数就是模型权重，光在结构中的传播就是一次前向推理。

核心循环：

```text
选择模型目标 / 蓝图
-> 摆放输入端口、波导、分束器、MZI、非线性介质、光RAM、输出探测器
-> 光控制核扫描结构并编译为 OpticalCircuitGraph
-> 校准台注入校准脉冲，写入相位偏置和损耗画像
-> 输入 InfoSignal，触发一次抽象光传播
-> 诊断台显示瓶颈：断路、相位漂移、相干能不足、光RAM 衰减、算子不匹配
-> 玩家改造拓扑、替换晶体、重新校准
```

方块语义：

| 物理结构 | 模型语义 | 关键状态 |
| --- | --- | --- |
| 输入端口 | 输入张量 / 传感器绑定 | `input_shape`, `signal_type`, `source_id` |
| 硅光波导 | 数据边 / 激活传输 | `loss`, `wavelength`, `route_id` |
| 分束器 / 合束器 | broadcast / concat / residual merge | `split_ratio`, `merge_mode` |
| MZI 阵列 | 矩阵层 / 卷积近似 / FFT | `phase_bias_vector`, `matrix_shape`, `calibration_age` |
| 相位调谐器 | 权重写入 / 权重微调 | `phase_offset`, `write_precision` |
| 非线性介质 | 激活函数 / 稀疏门控 | `threshold`, `s_curve_profile`, `pulse_drift` |
| 光RAM 循环腔 | 短时状态 / tick delay / recurrent state | `remaining_life`, `read_count`, `refresh_cost` |
| 输出探测器 | 输出张量 / 动作建议 / 诊断读数 | `output_shape`, `confidence`, `error_flags` |
| 光控制核 | 控制流 / 路由 / 任务调度 | `fsm_state`, `logic_error_rate`, `task_queue` |

结构编译规则：

- 光控制核只在结构变化、玩家手动重扫或校准完成时编译拓扑，不每 tick 扫描全结构。
- 编译结果是抽象图 `OpticalCircuitGraph`，只记录节点、端口、边、shape、波长、损耗和预算，不模拟真实连续光学。
- 方块位置决定连接关系，方块数据决定算子参数。玩家的主要决策是拓扑、晶体质量、相位校准和相干能预算。
- 模型蓝图只给目标形状和约束，不自动替玩家摆完整结构。高级蓝图可以显示轮廓投影，但仍需玩家放置关键方块。
- 允许“能跑但低分”的结构。错误应以诊断形式反馈，而不是只给失败提示。

最小可玩样例：

```text
传感器输入端口
-> 4 通道波导
-> 2x2 MZI 小矩阵
-> 非线性介质
-> 光RAM 1 tick 延迟
-> 输出探测器
```

该样例可表达一个小型感知-判断模型：输入机器状态，输出“继续运行 / 暂停 / 请求维护”等离散动作。玩家能通过更换高品级晶体、减少波导弯折、提高相干能、降低读取次数来提升稳定度。

失败与诊断：

| 问题 | 表现 | 玩家处理 |
| --- | --- | --- |
| shape 不匹配 | 输出端显示维度错误 | 改合束器、分束器或 MZI 尺寸 |
| 光路断开 | 节点无输入，光纤不发光 | 补波导或调整端口朝向 |
| 相位漂移 | 推理分数逐渐下降 | 重新校准或升级相位调谐器 |
| 相干能不足 | 光路闪烁，吞吐降低 | 增加稳谱晶体、激光源或降低并发 |
| 光RAM 读取衰减 | 状态输出越来越弱 | 降低读取频率、增加刷新或改短状态链 |
| 控制核错误率高 | 随机路由或任务重试 | 使用更高品级双稳态晶胞 |

这个玩法的价值在于把“模型优化”转化为 Minecraft 内可见、可摆、可诊断的结构问题：同一个蓝图可以有紧凑高速、低损耗高成本、可维护但冗余等多种物理实现。

### 10.4 内存、存储与带宽

内存主要影响：

- 参数缓冲区。
- 激活缓存。
- 历史序列。
- 状态寄存器。
- 经验回放。
- 数据集缓存。
- 模型版本。

存储主要影响：

- 数据集持久化。
- 日志。
- 模型保存。
- 参数快照。
- 实验记录。

带宽主要影响：

- 传感器数据流。
- 模型内网激活转发。
- 外网数据上传。
- 参数同步。
- 模型下发。
- 多模态大输入。

### 10.5 性能画像

系统不应武断限制玩家搭建规模，而是提供压力测试台和诊断设备。压力测试给出当前客户端或服务器适合的推荐规模：

- 推荐实时推理节点数。
- 推荐高频传感器数。
- 推荐并发训练任务数。
- 推荐历史缓存窗口。
- 推荐路由包吞吐。
- 推荐脚本指令预算。
- 推荐矩阵算子预算。

玩家可以超出建议，但系统应显示风险等级。性能画像应服务于模型设计，而不是独立成为主线。

## 11. 传感器系统

传感器是整个系统的数据入口。Minecraft 世界本身是离散、可查询、带标签、可结构化的，因此视觉和环境感知可以直接量化，而不必从真实像素中重新识别语义。

### 11.1 传感器类型

- 空间传感器：方块类型、亮度、硬度、流体、红石强度、距离、方位、可通行性、局部地形网格。
- 时间传感器：tick、随机刻、方块更新、生长进度、机器状态变化、日夜周期、天气变化。
- 历史传感器：最近 N tick 轨迹、奖励历史、库存变化、路径失败点、交互对象、状态摘要。
- 实体传感器：生命值、速度、朝向、目标、仇恨、背包、行为状态、关系值、攻击冷却。
- 物品/标签传感器：物品 ID、标签、NBT 摘要、数量、耐久、价值、合成用途、稀有度。
- 语义/API 传感器：把复杂世界状态编码为结构化文本或 JSON，供外部模型或高级脚本使用。

### 11.2 输出类型

所有传感器输出都应类型化：

- scalar
- vector
- grid
- sequence
- event
- tagset
- text
- graph

多模态由不同传感器自然组合而成，例如局部环境 grid、实体 state、物品 tagset、历史 sequence 和 API text 共同进入融合脚本或模型。

### 11.3 数据元信息

建议统一数据描述格式：

```text
name
type
shape
dtype
timestamp
source_id
confidence
cost
```

这套元信息服务于脚本处理、路由、缓存、训练日志、可视化和外部 API。

### 11.4 传感器接入方式

传感器可以有两种接入方式。

```text
直接接入模型外网
传感器 -> 输入网关 -> 模型
适合少量低频传感器，结构简单，延迟低。

独立传感器网络
传感器组 -> 传感器汇聚器 -> 融合处理器/缓存 -> 数据库或模型
适合大量传感器、远程采样、时间戳对齐和训练数据归档。
```

独立传感器网络不是强制层级，而是在这些场景中提供收益：

- 传感器数量多。
- 采样周期不同。
- 需要多源时间戳对齐。
- 需要把样本批量压缩上传。
- 需要缺失值、异常值和置信度标记。
- 需要把原始样本保存为训练数据集。

传感器网络节点：

```text
sensor_node：单个传感器或小型传感器组。
sensor_hub：本地汇聚，提供时间戳、缓存和基础过滤。
sensor_backplane：大量低速输入端口，常用于机器框架和信息中心。
edge_sampler：远程采样与本地预处理。
fusion_processor：多源融合，输出 vector/grid/sequence/event。
dataset_uploader：批量上传数据库、参数库或训练节点。
```

传感器网络输出仍使用统一数据元信息，因此模型不需要关心数据来自单个传感器、汇聚器还是远程边缘节点。

### 11.5 数据处理链路

数据处理应作为可搭建链路，而不是隐藏在模型输入黑箱里。

```text
raw SensorFrame
-> filter
-> timestamp_align
-> normalize
-> feature_select
-> fuse
-> batch_or_window
-> Input packet
```

每个处理节点都应暴露成本：

```text
script_ops
sensor_ops
route_ops
memory_pages
latency_ticks
confidence_delta
```

这样玩家能明确看到瓶颈来自采样、融合、脚本、路由还是模型本体。

## 12. 脚本器与指令集

脚本器既用于运行期数据预处理，也用于编辑期批量配置和元编程。

主要职责：

- 归一化。
- one-hot/tag embedding。
- 网格展开。
- 序列截断。
- 滑动窗口。
- 多传感器融合。
- 噪声过滤。
- 特征选择。
- 批量 ID 绑定。
- 维度 reshape。
- 稀疏化/压缩。
- 量化转换。

建议分两层：

- 高级领域脚本：面向传感器、路由、模型输入、量化和多模态融合。
- 底层 VM/指令集：可参考 WASM、Lua VM、Forth、RISC-V 子集或 eBPF 风格指令集。

运行期脚本应尽量编译为固定数据处理图；编辑期脚本可以用于批量创建、修改、重命名、绑定和转换 ID。

脚本器必须沙箱化：

- 最大指令数。
- 最大内存。
- 最大执行时间。
- 网络权限。
- 外部 API 权限。
- 每 tick 调用次数。
- 递归和动态代码限制。

## 13. 损失、反馈与训练

损失和反馈不应作为独立于模型图之外的特殊系统。它们本质上仍然是“数据节点/传感器 + 算子 + 路由”的组合，只是容量、生命周期、参数量和使用方向与普通推理数据不同。

统一表达：

```text
观测数据 -> 评价算子/损失算子 -> feedback 数据节点 -> 回流路由 -> 优化器/状态更新器/日志
```

例如：

```text
目标位置 + 当前实体位置 -> 距离损失算子 -> loss.distance
碰撞事件传感器 -> 惩罚算子 -> reward.collision_penalty
库存历史 + 目标库存 -> 误差算子 -> metric.stock_error
对话结果传感器 -> 评分算子 -> reward.trade_success
```

这意味着 loss、reward、metric、gradient 都可以被同一套数据描述、路由 ID、脚本器、可视化和存储系统处理。

反馈信号不只包括监督学习中的 loss，也包括 reward、惩罚、资源约束、延迟、能耗、稳定性和对抗结果。

建议标准格式：

```text
source_id
target_id
value
type: reward/loss/gradient/metric
timestamp
confidence
```

反馈来源：

- 生物任务：距离目标变化、碰撞、耗时、生存、伤害、交易成功率、关系变化。
- 物流任务：堵塞率、库存误差、机器空转、吞吐、缺货、能耗。
- 通信任务：延迟、丢包、拥塞、认证失败、数据污染。
- 性能任务：推理延迟、资源占用、热量、队列长度。
- 外部 API：评分、动作建议、参数更新、训练指标。

反馈回流可以进入模型内网触发局部参数更新，也可以经外网上传到中心训练节点，等待批量训练、蒸馏或策略回传。

### 13.1 反馈节点也可以有参数

损失/反馈节点本身也可能引用参数或状态，例如：

- 多目标损失权重。
- 奖励缩放系数。
- 碰撞惩罚阈值。
- 平滑窗口。
- 任务难度系数。
- 对抗评分器参数。
- 外部 API 评分置信度。

因此反馈节点应与普通算子共享同一套参数系统。一个反馈模块可以拥有自己的参数方块，也可以引用外部参数库中的权重；这些参数同样可以被冻结、复制、量化、版本管理或被更高层优化器调整。

### 13.2 反馈节点的容量差异

反馈节点与普通推理节点的区别主要在容量和使用方式，而不是底层类型：

- 普通推理节点通常高频、低延迟，直接服务输出动作。
- 损失/反馈节点可以低频、延迟容忍，服务训练、评价、日志或策略更新。
- 简单反馈可能只输出一个 scalar。
- 复杂反馈可以输出 vector、sequence、event 或带标签的 metric 包。
- 本地反馈可在模型内网直接回流。
- 大规模反馈可经外网上传到中心训练节点或实验日志台。

这样一来，监督学习、强化学习、控制优化、对抗评分、物流评价和性能诊断都可以用同一套数据图表达。

## 14. 数据质量与实验管理

模型效果应当受数据质量影响，而不是只由模型规模决定。

可设计的数据质量因素：

- 噪声。
- 缺失值。
- 延迟。
- 偏差。
- 样本不均衡。
- 标签错误。
- 过期数据。
- 重复样本。

对应工具：

- 数据清洗器。
- 过滤器。
- 重采样器。
- 平衡器。
- 特征选择器。
- 数据集版本柜。
- 实验日志台。

实验管理应记录模型版本、数据集版本、参数快照、指标曲线、训练配置、最佳结果、A/B 测试和回滚点。

## 15. 可视化与诊断

可视化是核心玩法，不是附属 UI。玩家需要看见抽象系统在运行。

建议设备：

- 数据流示波器。
- 损失/奖励曲线屏。
- 参数热力图。
- 路由流量图。
- 传感器视野投影。
- 网络拥塞图。
- 性能分析屏。
- 对抗回放器。
- NaN/爆炸梯度/异常反馈警报器。

诊断器应指出：

- 哪个传感器扫描太频繁。
- 哪个脚本耗时高。
- 哪条路由广播过多。
- 哪个模块重复计算。
- 哪个历史缓存占用大。
- 哪个输入模态贡献低但成本高。
- 内网瓶颈还是外网瓶颈。
- 信号链路瓶颈还是光路结构瓶颈。

## 16. 外部 API 与真实后端

外部 API 是扩展能力，不应吞掉游戏内系统。

边界：

- 游戏内定义数据、任务、结构、约束和指标。
- 外部后端负责可选的训练、推理或优化。
- 返回结果必须结构化。
- 有延迟、成本、失败、权限、限流和超时。
- 服务器可禁用或限制外部调用。
- 需要离线 fallback 或本地简化模式。

可支持的后端方向：

- 本地 Python/PyTorch/Sklearn/Optuna 服务。
- 外部 LLM/API 评分或对话服务。
- 训练任务队列。
- 模型注册表。
- 参数或策略回传接口。

## 17. MVP 建议

第一版不追求完整 CNN、RNN、MoE、Diffusion，而是验证最小闭环。

目标实验：

```text
让玩家拿到一块卡玛恩晶体，读取它的频谱/张量/应力画像，通过爆炸室改变画像，再用探针输出 `InfoSignal` 并触发一个红石或机器行为。
```

需要实现：

- `KamaenCrystalComponent`：频谱签名、三轴张量、应力、噪声、相干度和专化倾向。
- 晶体 tooltip 或简易读取 UI：频谱条、三轴倾向、稳定度和未知字段遮罩。
- 爆炸室最小 BlockEntity：按结构评分写入/改变晶体画像。
- `InfoSignal` 与 `IKamaenReadable` 白名单接口。
- `info_probe` 右键晶体/方块的读取交互。
- 频率总线和红石转换模块的最小相邻网络。
- 诊断报告：晶体是否不稳定、频谱是否匹配、信号是否衰减、路由是否拥塞。

这个 MVP 可以验证“晶体是信息材料”的核心玩法。之后再把输出从“红石/机器触发”扩展到“频率总线缓存”“结构模型编译”和“全光模型输入”。

## 18. 后续落地拆分

后续进入开发时建议按以下顺序拆分：

1. 数据类型与元信息格式。
2. 参数方块、参数矩阵板和参数库的数据结构。
3. 算子描述格式与封装模块格式。
4. local/export/remote ID 与命名空间规则。
5. 模型内网运行环境。
6. 内部触发器与子图调度。
7. 传感器基类与首批传感器。
8. 脚本器最小语法或数据处理图。
9. 频率总线、信号缓存和固定数据包类型。
10. 模型外网网关与存储/执行器连接。
11. 可视化屏幕与诊断工具。
12. 性能测试台与性能档案。
13. 通信层原型。
14. 模型组件方块网络与模型编译器。
15. 外部 API 网关。

## 19. 核心原则

- 先做晶体画像与信息读取闭环，再扩展科技流程。
- 参数方块与算子参数系统完全统一。
- 有参数算子优先封装为模块，内部由脚本或子算子网络描述。
- 游戏表现可以是方块、ID、触发器和路由，运行时应编译为可执行图与连续缓冲区。
- 模型内网负责局部异步计算，模型外网负责世界数据、远程通信和外部服务。
- 触发器提交任务，路由系统移动和组织数据；第 5 阶段由频率总线和信号缓存组织信息，第 6 阶段由光控制核调度全光结构。
- 高吞吐计算由第 6 阶段光GPU、光脉冲处理器和光协处理器处理。
- 模型规模、传感器频率、脚本复杂度、路由跳数和通信网络都应有可测量成本。
- 外部 API 是高级扩展，不是绕过游戏内信息系统的万能答案。
- 游戏内限制优先通过测量、诊断和风险提示表达，而不是武断禁止。
