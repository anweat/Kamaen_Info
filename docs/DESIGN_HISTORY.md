# Kamaen Info 设计演进历史

本文档收录主要设计决策的演进过程、旧想法的原貌，以及每次变更的原因。它不是当前设计的规范，而是设计过程的记录，供未来迭代参考。

---

## 决策 0：算力系统改为多工艺 EDA（v0.7，2026-06-17）

### 背景

早期文档曾在“电气芯片/主板”和“全光五件套”之间摆动：先考虑用电逻辑门构造芯片和主板，随后又收束为全光计算。新的方向不是简单恢复旧电气 CPU/GPU/NPU，而是把芯片设计扩展为 EDA 玩法：电、光、量子微逻辑门，以及存储、互连、冷却管线都作为可选元件库。

### 新决策

算力系统采用“多工艺 EDA + 环境域隔离”：

```text
电逻辑门
  → 早期接口、桥接、经典存储、低速控制

光逻辑门
  → 第 6 阶段主计算路线：光控制核、光GPU、光脉冲处理器、光RAM

量子微逻辑门
  → 第 8 阶段协处理路线：单光子、测量、纠缠、误差校验、蓝图采样

存储/冷却/互连
  → EDA 中可放置的工程元件，不再只是隐藏属性
```

硬约束：不同物理环境的主逻辑不能在同一裸片中无隔离混放。电、光、量子区域可以在同一算力节点中协作，但必须通过封装、桥接器、低温/相干/散热接口连接，并显式结算延迟、噪声、相干能和冷却预算。

### 与 v0.4 全光路线的关系

v0.4 的全光五件套仍然成立；它现在是 EDA 体系中的 `photonic` 主计算工艺族。旧电气 CPU/GPU/NPU 不恢复为中游主线，电逻辑只承担接口、桥接、低速自动化和早期兼容任务。量子微逻辑作为后期协处理工艺族，不替代全光五件套。

详细规范见 `docs/Kamaen_Info_Computing_EDA_Design.md`。

## 决策 1：全光计算架构（v0.4，2026-06-03）

### 旧设计（v0.3）

**架构名称**：电光混合三件套

```
电气 CPU（electric_cpu_module）
  → 分支/控制/调度/路由/脚本/IO（全部由电气路径承担）

光协处理器（photonic_coprocessor）
  → CPU 调度下的数据搬运加速（电控 + 光数据）

光GPU（photonic_gpu_unit）
  → MZI 干涉网络做密集矩阵运算

电NPU（electric_npu_unit）
  → 稀疏激活、量化推理、特殊算子（全部电气）
```

**v0.3 的论点**（当时认为成立的）：
> 光逻辑门、光存储、光分支在工程上至今无成熟方案。光的强项是无干扰并行传输和密集线性运算，弱项是非线性、分支和持久存储——这恰好是 CPU 的核心职责。保留电气 CPU + 新增光协处理器是更自洽的分工。

### 变更原因

1. **核心问题**：卡玛恩晶体的参数（应力张量、频谱、χ⁽²⁾ 非线性系数）在第 2 阶段被写入，但直到第 6 阶段才被利用。旧设计中第 6 阶段的主角是「电气CPU + 光GPU」，晶体只是光GPU 里的波导材料，参数路径断裂。

2. **设计一致性**：模组的核心叙事是「晶体是计算介质」。如果控制路径（CPU）仍然是纯电气的，这个叙事就是不完整的。

3. **费曼桥接**：第 7-8 阶段的费曼过程蓝图要求玩家理解「激发顶点」和「湮灭顶点」。如果第 6 阶段的控制路径是电气的，这个桥接就没有语言基础——玩家在第 7 阶段看到费曼图时无法回溯到自己使用过的物理过程。

4. **卡玛恩晶体的游戏设定赋权**：真实物理中光逻辑门的瓶颈（光子-光子相互作用弱）可以用「卡玛恩晶体的 χ⁽²⁾ 非线性」这一游戏设定补充。v0.3 的论点是在不引用游戏设定的情况下得出的，因此过于保守。

### 新设计（v0.4）

**架构名称**：全光五件套

```
光控制核（photonic_control_core）
  → 卡玛恩双稳态晶胞 + 光逻辑门阵列 = 全光 FSM
  → 承担原电气 CPU 的全部职能，但所有信号路径为光子

光协处理器（photonic_coprocessor）
  → 不变：光数据通路、批量搬运

光GPU（photonic_gpu_unit）
  → 不变：MZI 网络矩阵运算

光脉冲处理器（photonic_pulse_processor）
  → 承担原电NPU 的全部职能：稀疏激活（饱和吸收体）、激活函数近似（S 型传输曲线）

光RAM（photonic_ram_unit）
  → 新增：受激辐射循环腔，短时状态存储（原电NPU 的片上 SRAM 的光学对应）
```

**核心物质基础**：
```
稳谱晶体 + 应力张量 → 调谐的 χ⁽²⁾ 非线性系数
导波晶体 → 光子限域，增强非线性相互作用
→ 卡玛恩晶体提供了真实物理中不成立的光逻辑条件（游戏设定）
```

### 保留的旧想法

- MZI 干涉网络做矩阵运算：**完全保留**，原始设计正确
- 相干能作为独立资源：**完全保留**
- F4 光频协议三层用途：**扩展保留**（新增光控制核 FSM 时钟层）
- 光路校准机制：**保留**
- 光GPU 表面干涉条纹可视化：**保留**

## 决策 2：FE 与相干能的职责分离（v0.4，2026-06-03）

### 旧设计（v0.3）

FE 和相干能并行存在，但职责界定模糊：
- 相干能在第 4 阶段就作为「将 FE 整理为低噪工艺能源」出现
- 但机器的基本驱动用 FE，高精度工艺用相干能
- 这个区分是隐含的，没有在设计原则层面明确说明

讨论过的方向：完全抛弃 FE，用模组自定义能量替代

### 变更原因

1. 完全抛弃 FE 的代价：打破与其他模组的互操作性；需要重设计发电逻辑；对早期玩家（已熟悉 FE 生态）不友好。

2. 更好的做法：**明确职责**而不是替换：
   - FE = 热力学功（让机器运转，提供物质生产能量）
   - 相干能 = 信息传播（承载计算和精密工艺）
   - 晶体 = 桥梁（FE 通过机械应力写入晶体；相干能通过光读出晶体）

3. 这个分离本身就是一个值得玩家理解的物理概念：做功（能量）和编码（信息）是不同的事。

## 决策 3：物理结构即模型（v0.4，2026-06-03）

### 背景

用户提出：「光计算实际就是用摆出的模型去往一块晶体里写模型参数和计算迭代过程，类似于现实中的光 diffusion 实验芯片」

### 旧设计（v0.3）

光GPU 的模型由「权重写入 = MZI 相位烧录」实现。玩家的操作是「触发校准，等待权重写入完成」，不是「搭建物理结构」。模型架构由抽象的「模型物品」携带。

### 新设计方向（v0.4 提出，v0.5 补具体玩法）

光计算系统应向「物理结构即模型」方向延伸：
- 玩家摆放方块的拓扑 = 模型架构（网络连接）
- 晶体参数（应力张量、频谱）= 权重（通过早期合成工艺「训练」进晶体）
- 光在结构中传播 = 前向推理
- 多次迭代 = 扩散/优化过程

v0.5 已在 `Kamaen_Info_Information_System_Design.md` §10.3 补充具体玩法：输入端口、波导、MZI、非线性介质、光RAM、输出探测器组成可编译的 `OpticalCircuitGraph`，并通过校准、诊断和光RAM 衰减形成可玩的优化循环。

## 决策 4：「激发-湮灭」作为跨阶段统一语言（v0.4，2026-06-03）

### 背景

第 6 阶段光计算和第 7-8 阶段费曼过程蓝图之间存在叙事断层：玩家使用光逻辑门时不知道这跟后来的费曼图有什么关系。

### 新设计

将「激发-湮灭」定义为第 6 阶段开始就使用的操作语言：
- 激发：光子被晶体共振腔捕获 → 声子模式激活（第 6 阶段中的光逻辑操作）
- 湮灭：声子模式弛豫 → 定向释放光子（第 6 阶段中的信息读出）

这与第 7 阶段费曼图的「吸收顶点」/「发射顶点」直接对应，第 8 阶段的量子光学协处理器进一步将这些顶点与 â†/â 算子联系。

跨阶段连续性：
```
第 6 阶段：宏观系综（大量光子，经典相干）
第 7 阶段：中观费曼图（顶点集）
第 8 阶段：量子叠加（â†/â 算子）
```

## 决策 5：为什么不放弃科技树的「信息系统」方向（持续原则）

有时候讨论中会出现「这不是太复杂了吗」的质疑。保留这个方向的理由：

1. **差异化**：Minecraft 模组大量做的是「合成→产线」循环。信息系统给了玩家「观察、诊断、理解自己搭建的系统」的体验，这在现有模组生态里稀少。

2. **主线不强制**：所有信息系统功能都是**可选深度**。固定工艺窗口可以完成主线；信息系统是给想玩深的玩家的上限。

3. **「宏大概念有限化」是核心设计原则**：黑洞、费曼图、维度创世都不是在 tick 内真实运行物理，而是把概念落到有限、可诊断的方块系统里。信息系统也遵循同样的约束。

## 废弃的设计方案（存档）

### 废弃：「电气 CPU 升级路径」

v0.3 曾计划 `electric_cpu_module` 有多个升级等级（CPU Tier 1/2/3），以晶体管数量和时钟频率为指标。

废弃原因：升级 CPU 变成「堆数字」，缺乏物理意义。改为光控制核后，升级路径变成「提升晶体品级 → 提升 χ⁽²⁾ 非线性 → 降低逻辑错误率」，有物理意义且与早期工艺挂钩。

### 废弃：「光CPU」命名

用户曾提出直接叫「光CPU」。

废弃原因（v0.3 时期论点）：工程上不成立（无成熟方案）。
实际解决方式（v0.4）：用「光控制核」命名 + 卡玛恩晶体游戏设定作为物质基础，避免直接挑战工程常识但也不用电气路径。

### 废弃：完全替换 FE

用户曾讨论完全用模组自定义能量替代 FE。

废弃原因：互操作性代价 + 早期玩家适应成本，而实际设计目标（区分热力学功和信息传播）通过「明确职责」而不是「替换」就能实现。
